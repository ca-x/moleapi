# ZooKeeper provider discovery acceptance fixture

This isolated Maven project uses Apache Dubbo3.3.6, Curator5.8.0 and embedded ZooKeeper3.9.2 (from Curator's resolved dependency graph). It registers one grouped/versioned Dubbo provider, calls the official `RegistryService.lookup`, checks group/version filters and proves lookup did not invoke the business method. A normal run calls that provider directly once, unexports it and waits for the registry record to disappear. `--hold` keeps the provider available so `verify.py` can pass the exact original registry URL to Rust's complete-snapshot admission and then the pinned official direct worker. No application registry mode or user endpoint is enabled by this fixture.

The local isolated toolchain used SHA512-verified Maven3.10.0, the pinned Temurin JRE21.0.12.1+1 and checksum-verified ECJ3.43.0 to compile the same Java source; Maven's checksum-verified dependency copy supplied the runtime graph. Local runs passed official lookup/removal, checked Rust provider selection, a real grouped RPC and hosted private-address refusal. The manual `Classic Dubbo interoperability QA` workflow runs the Maven/JDK build and retains JSON evidence plus bounded Java logs. Its CI result must be read before claiming that particular runner passed.

The official Java RegistryFactory needs the provider's initialized `ApplicationModel`: construct `ZookeeperRegistryFactory(applicationModel)` and call `setApplicationModel(applicationModel)` before `getRegistry`. A no-arg factory compiles, but `getRegistry` fails because its `RegistryManager` bean is unset. The ZooKeeper build also needs Curator's `curator-x-discovery`; a compile-only fixture misses this runtime dependency. These are QA source findings, not reasons to bypass the mature SDK.

The next product slice is a bounded one-shot discovery worker which must connect only to a Rust-checked registry address and return provider URLs as data. Current Rust URL admission and selection remain unused by product execution. Nacos and EDAS, metadata import, credentials and TLS/proxy modes need separate real fixtures and policy gates.

The ZooKeeper source is now wired through the product runtime and editor. The fixture builds the Rust example before starting the held Java provider, registers two versions/groups, and verifies Rust filters the raw nodes the same way Apache lookup does. It compares the selected raw child with Apache's normalized lookup at the destination and service-control level, uses that raw child for a pinned Rust RPC, and separately exercises `DubboRuntime::invoke` with the ZooKeeper source. Apache lookup strips `timestamp` and adds `check=false`, so byte-for-byte URL equality is incorrect. Authentication, Nacos, EDAS, metadata, and installed-app acceptance remain separate work.
