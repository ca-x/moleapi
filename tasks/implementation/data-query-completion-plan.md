# Data query completion plan

Authority: `docs/specs/data-query-completion.md`. This plan orders one capability map; each numbered part is independently testable but the user-facing feature is not complete until all three are wired.

1. Add bounded `DataCompletion` output to the protocol session's Data control. Deliver one result/error/cancel outcome per terminal query, preserving the existing Data events and no-retry behavior. Test channel full/closed, cancellation and completed query identity with an actual file worker.
2. Add an owner-fenced server consumer at Data session creation. Convert `QueryResult` into a versioned `Response`, run the shared assertion/extraction/post-script workers and emit `data_processed` or `data_postprocess_error`. Reuse existing variables/privacy helpers; do not duplicate JavaScript or JSONPath logic. Test that post scripts run once, required extraction failure is visible, updates remain scoped, and logout/delete prevents stale output.
3. Persist bounded Data history through the existing owner/workspace history store. Preserve typed database rows only under the 5 MiB body budget; withhold file-backed rows and uncertain private/script-failure output. Test saved/restored/cleared history, user isolation, oversized bodies, SQL error and cancelled-write wording. Extend the Data workbench to display postprocessing status and navigate to the saved record.
4. Run scoped Rust/front-end tests, strict Clippy, formatting, production frontend/embedded build, actual hosted database and file fixtures, 390px browser QA, then branch CI and current platform gate. Review findings before merge; record remaining per-query pre-script and broader product gaps explicitly.
