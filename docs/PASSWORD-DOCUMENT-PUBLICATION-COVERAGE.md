# Password-protected publication coverage

Scope: the password option of `documentation-004` and the corresponding reader gate of `documentation-011`, specified in [password-protected-document-publications.md](specs/password-protected-document-publications.md). Existing public snapshots remain valid without a password; this does not claim full audience/role parity.

An owner can select Public or Password when creating an immutable Markdown publication. Password mode requires 10–128 UTF-8 bytes and stores only a salted Argon2id hash inside the hosted publication row, outside workspace backup/sync. The owner list reports access mode, never the password, hash or failed-attempt state. The idempotency digest includes mode but not the password; a same-key/same-password retry returns the active version, while a different password or revoked key conflicts. Public mode rejects a supplied password.

The active password publication's HTML shell contains no snapshot. Anonymous JSON GET returns 403 without title/source; `POST /api/public/docs/{id}/unlock` returns the snapshot only for the correct password. The public page holds the submitted password until the request settles, clears the field, and keeps the unlocked snapshot only in component memory. Reload requires another unlock. Failed attempts share a database-time five-minute sliding window and publication-row lock across hosted instances: ten failures return generic 401, then further attempts return 429 with `Retry-After`. At most ten sorted failure timestamps are stored; no IP or password attempt body is stored. Wrong, malformed, throttled, missing and revoked responses include no-store, no-referrer, nosniff and restrictive CSP headers; the HTML page applies its own restrictive CSP and 404 after revocation.

Local evidence: hosted route tests cover validation, public-mode compatibility, owner metadata screening, locked GET, wrong/correct unlock, idempotent same/different password, no source before unlock, malformed-request headers and revoked HTML/unlock 404. The configured database test locally passed on SQLite with two app instances alternately making ten wrong guesses, a cross-instance 429 and `Retry-After`, then revocation. A pure sliding-window test covers expiry, a new attempt at the expiry edge, future timestamps and unordered state; PostgreSQL/MySQL require their configured CI endpoints. The full frontend suite passed 421 tests; TypeScript, production 46-chunk build, scoped strict server Clippy and refreshed embedded server build passed. The final binary served the active password HTML shell and returned 403 for anonymous JSON GET.

In a real hosted browser, an owner published a password version beside existing public/private workspace content. A separate anonymous 390 px browser saw neither title nor body before unlock; wrong password cleared the field, correct password showed the snapshot and local search, refresh returned to the locked form, and neither local nor session storage contained the test password. Revocation made both HTML and unlock return 404. The refreshed embedded server returned no-store/no-referrer/nosniff/CSP headers on locked GET, malformed unlock and missing HTML paths. The locked page remained 390 px wide and axe reported zero violations and zero incomplete checks. The owner panel remained 390 px wide; axe reported zero violations and one incomplete theme/background contrast inference.

Independent read-only review found no confirmed Critical or Important issue. It identified two lower-priority response-contract gaps: malformed/oversized unlock input could precede a missing/revoked 404, and framework-generated 413 responses lacked public cache/CSP headers. The handler now checks publication state before parsing errors, and an outer public-doc API middleware applies headers after framework error processing. Focused regressions and independent re-review passed; the final embedded binary returned 403 with no-store/CSP for locked GET, 404 with headers for invalid HTML, and 413 with no-store/no-referrer/CSP for oversized unlock input.
