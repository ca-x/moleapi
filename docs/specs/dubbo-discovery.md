# Classic Dubbo provider discovery and metadata import

This extends `dubbo-client.md` and matrix row `protocols-015` beyond direct calls. Apifox documents ZooKeeper, Nacos and Alibaba Cloud EDAS registry selection, plus provider metadata-center import. Registry discovery and metadata import are distinct: the first finds a provider for one call, while the second reads service/method/parameter definitions into an editable source bundle.

## Source and selection

- A versioned Dubbo request may select `direct` or `registry`. Registry source names the provider (`zookeeper`, `nacos`, `edas`), registry endpoint/region/namespace, target service/version/group and explicit credentials. An optional metadata-center source is separate. Direct requests retain the existing exact source and defaults.
- Save the original registry and metadata references, even when a current instance cannot connect. No URL, service, method or argument is rewritten into the canonical workspace after discovery. Explicit source export can preserve credentials; default backup, history and reports screen them. External Postman/OpenAPI exports refuse unsupported Dubbo source.
- Discovery returns a bounded set of provider URLs and provenance, not an already opened provider socket. The user can inspect which provider was selected. Registry and metadata responses are treated as untrusted remote data.

## Checked two-phase call

1. Resolve every registry/metadata destination address under the existing owner and network policy. Pass only a checked literal IP to an isolated mature SDK worker, preserving the original logical name only where the SDK can safely use it for TLS/SNI/authentication. Unsupported TLS/proxy/DNS settings reject explicitly.
2. Ask Apache Dubbo's registry API for a one-shot provider snapshot matching service/version/group and provider category. The worker must not register this client as a provider, start QoS, expose a listener, execute provider RPCs or cache credentials to disk. Bound startup, response bytes, provider count and URL size; cancellation kills and reaps it.
3. Rust validates every returned provider URL's scheme, service/version/group/serialization and all resolved IPs. It rejects mixed safe/unsafe address sets under hosted policy. It deterministically chooses one validated provider and passes its pinned IP to the existing direct GenericService worker. No Java re-resolution of provider names.
4. Discovery and invocation have one user-visible deadline. On failure, report whether registry lookup, provider admission, connection or remote method failed. Do not replay an ambiguous method result or silently switch to another provider after a request has begun.

Registries are eventually consistent. A provider can disappear after lookup, so a validated snapshot is an address selection, not a guarantee of availability or a transaction. No persisted or cross-owner provider cache is required for the first slice; each explicit call rechecks registry and selected provider. A later bounded cache must state its staleness and revision rules.

## Metadata import

Use Apache Dubbo's provider metadata service/metadata report APIs to read provider-advertised package, interface, method, parameter and response definitions. Import is explicit, owner-scoped, capped and cancellable. Preserve the original metadata document/provenance and present a preview/diff before applying it to a workspace; never overwrite authored definitions without a selected conflict decision. Dubbo providers without metadata-center reports, or Dubbo versions/options the engine cannot decode, return an explicit unsupported result. Metadata endpoints follow the same checked-address and credential rules as registries.

## Acceptance evidence

- Separate real ZooKeeper and Nacos provider fixtures cover lookup, version/group filtering, provider removal/change between calls, registry auth, malformed/oversized URLs, empty results, cancellation and private-network refusal. Independent Java services answer the selected direct RPC, proving the provider endpoint came from registry output and was rechecked/pinned by Rust.
- EDAS uses an explicit test account/sandbox or equivalent provider-approved fixture; API name, region/namespace, credential scope and endpoint behavior are verified separately. Compile-only SDK use or a generic registry selector does not count.
- Metadata import demonstrates original source and method/DTO mappings, owner isolation, private export, preview/conflicts and exact restore. Missing/unsupported metadata remains visible without fabricating a definition.
- Bilingual editor and actual browser/native flows show registry/source selection, selected provider, errors and cancellation at390px. Three databases, installed packages, embedded resources and container smoke remain the unified release gate.

Source: retained hash-checked Apifox `create-dubbo-api.md` and `debug-dubbo-api.md` under `docs/references/raw/`, plus Apache Dubbo3.3.6 `RegistryService.lookup(URL)`, `RegistryFactory` and metadata-report source. The direct worker is not a registry client merely because it accepts a `dubbo://` URL.

Current source checkpoint: Rust `dubbo_provider_url` validates the service path, exact version/group, provider side/category, Hessian2 advertisement, enabled state, credential-free URL and bounded/unique control fields. `select_registry_provider` caps the complete list, parses every result, checks every destination under one network-policy deadline, then preflights only a deterministic selected address. A malformed later result cannot be hidden behind an earlier reachable one. These functions are not a registry client: no ZooKeeper/Nacos/EDAS SDK lookup, metadata call or registry editor is wired yet.

ZooKeeper product checkpoint: source version 2 with `source=zookeeper` and a `zookeeper://host:port` request URL now performs a one-shot children lookup using a locally patched `zookeeper-async` SDK. Rust checks every resolved registry address and hands the SDK only a literal checked IP. The SDK patch caps inbound frames, strings and child count and aborts its background tasks on drop. Rust decodes the node names once, filters version/group as the official lookup does, checks the complete matching provider set, then pins one checked provider for the existing direct worker under the same call deadline. Malformed URL and duplicate version/group controls fail before filtering. The editor exposes direct/ZooKeeper selection and the live response console shows the selected pinned address; this initial source explicitly rejects URL credentials, chroot, query settings, TLS and proxy mappings. Apache's official lookup normalizes some node URL parameters, so exact text equality between its result and raw ZooKeeper children is not an acceptance condition; service/group/version and destination match, and the actual RPC uses the raw child URL after Rust admission. Nacos, EDAS, metadata import, ZooKeeper authentication, full provider provenance UI and platform release gates remain open.

Independent ZooKeeper QA now runs an actual Apache provider against Curator's embedded ZooKeeper: official `RegistryService.lookup` returned the original grouped/versioned provider URL without executing a business method, wrong group/version returned no providers, direct invocation answered once and unexport removed the record. An external Rust example consumed that exact URL, applied the full-snapshot checked policy, pinned its provider address and called the official direct worker; hosted private-network policy rejected the same private destination. This is local isolated fixture evidence, not product registry-mode support. Nacos/EDAS and metadata-center behavior remain unverified.

Digest source checkpoint: optional `registry_auth` holds explicit ZooKeeper username/password and is valid only for `source=zookeeper`. The SDK sends `add_auth("digest", "username:password")` under the same deadline after Rust pins the registry IP. A second real Apache provider creates ACL-protected nodes using that identity. Local QA proves anonymous and wrong-password reads fail, while SDK lookup and the product RPC succeed with the credential. Default native backup clears both fields; explicit private export retains them, and response-history redaction tracks both. The bilingual editor uses a password input and a saved/reloaded 390px browser call succeeded. Nacos/EDAS/metadata and a separate CI run for this latest credential slice remain open.

Nacos initial source checkpoint: `source=nacos` accepts a plain `nacos://host:port` endpoint with explicit Dubbo version and group, in the public namespace without registry authentication. Rust admits every resolved registry IP, pins one address for one HTTP GET to Nacos 2.5.1's published instance-list endpoint, disables proxies, redirects and compression, and caps response bytes and instance metadata. It turns healthy, enabled instance IP/port/metadata into a provider URL, then runs the complete matching-provider admission and fixed direct worker. An independent official Apache Dubbo3.3.6 provider registered into a real Nacos2.5.1 server; the mapped URL matched `NacosRegistry.lookup` byte for byte and answered a real product RPC. Wrong group/version, provider removal, hosted private-IP refusal and saved/reloaded 390px browser use were checked locally. The public HTTP route is a deliberate narrow equivalent to the planned SDK worker: Nacos' Java SDK opens an extra gRPC connection, whereas this documented read endpoint lets Rust pin its only discovery connection. Nacos authentication, namespace selection, EDAS, metadata import and package/database release gates remain separate required work.

Nacos namespace continuation: `registry_namespace` is an optional bounded namespace ID independent of the endpoint URL; empty selects public. The checked HTTP call adds Nacos' `namespaceId` query field, while the original request URL stays unchanged. A real Nacos2.5.1 namespace and Apache3.3.6 provider proved public isolation, exact URL agreement, selected product RPC and removal in both namespaces. The self-starting archive fixture and saved/reloaded 390px browser call passed locally. Nacos authentication, EDAS, metadata import and platform/database gates remain open.

Nacos authentication checkpoint: optional `registry_auth` also applies to `source=nacos`. After Rust admits every registry IP and pins one private address, the same bounded HTTP client POSTs username/password to Nacos' login endpoint under the shared deadline, accepts at most 16 KiB of login response and sends the access token in an Authorization header for one instance-list GET. It never writes the token into a URL or saved source. Authenticated Nacos over plaintext HTTP rejects public destinations; TLS remains unsupported pending a separate fixture. A real Nacos2.5.1 auth-enabled server and official Apache registry provider proved anonymous/wrong-password refusal, authenticated lookup/RPC, custom-namespace isolation and removal. Default backup screens credentials, explicit private export retains them, and a saved/reloaded 390px browser call succeeded locally. CI for this latest slice, EDAS, metadata import and platform gates remain open.

ZooKeeper metadata import checkpoint: a separate `metadata_center_url`, provider `metadata_application` and optional digest credentials are saved on the Dubbo source without rewriting its call endpoint. The owner-scoped preview pins every metadata destination under network policy, reads Apache's `/dubbo/metadata/<service>/<version>/<group>/provider/<application>` node with the bounded SDK, and returns the exact 1 MiB-capped original document plus checked method/parameter/return outlines and SHA256. Import requires a saved source request, collection, expected workspace revision, matching document SHA and an explicit action for each method. Existing matching methods default to skip; add creates a separate draft and replace requires the exact matching request ID. A fresh read rejects metadata changes between preview and apply. A linked `dubbo-metadata` specification stores the original document, metadata URL, checked document SHA, source request ID and pre-import workspace revision. Scalar arguments default to `null`; DTO arguments receive editable `$class`/`$` JSON drafts from the provider's bounded `types[].properties`, with null field placeholders. Generated requests do not duplicate metadata credentials. Default backup removes credential objects so the backup remains importable and screens nested sensitive metadata values; explicit export keeps originals. A real Apache3.3.6 provider with ZooKeeper metadata report produced the exact Rust preview, digest-protected nodes reject anonymous/wrong-password reads, and 390px browser preview/import/save/restore plus 401/404 owner checks passed locally. Nacos metadata report, EDAS, nested DTO/enum/collection editing and platform/database release gates remain open.

Nacos metadata public checkpoint: Apache3.3.6 `NacosMetadataReport` uses Nacos ConfigService with dataId `<service>:<version>:<group>:provider:<application>` and default config group `dubbo`. Rust resolves/adopts the checked literal endpoint, pins one HTTP ConfigService GET without proxy/redirect/compression, caps the body at 1 MiB, and feeds the exact bytes to the same bounded service/method/DTO parser. A real Apache provider on Nacos2.5.1 returned byte-identical content from official `getServiceDefinition` and fixed HTTP configuration lookup. Product preview/import select this path when the saved metadata URL has `nacos://`; user-provided Nacos metadata credentials are rejected explicitly. Custom metadata namespaces/groups, authenticated Nacos metadata, EDAS, deeper DTO editing and final release gates remain open.
