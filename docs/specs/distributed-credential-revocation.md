# Cross-instance credential revocation

Hosted instances sharing one supported relational database must observe token revocation and logout from other instances. Commit credential deletion and an owner revocation revision atomically using SeaORM transactions. Serialize concurrent owner revisions using the existing account row; reuse the internal settings table without storing plaintext credentials. Authenticate future calls against the database as before.

Each hosted router reads a startup baseline before accepting work, then polls revisions every second. Changed revisions invalidate the owner's protocol admission generation and stop existing jobs, protocol connections, webhook listeners and OAuth flows, clearing in-memory cookies through the shared invalidation path. Apply revisions once per instance under the existing owner gate, so local publication does not trigger a later duplicate cancellation. Track only the latest revision per account. Restarted instances baseline historical events rather than cancelling newly created work for an old event. Dropping the router cancels the poller; standalone/offline modes start no poller.

Propagation is eventual (one polling interval plus DB/cleanup time), not instantaneous cross-instance interruption. Poll failures retry without advancing consumed revisions; no external message broker is required. Natural credential expiry still denies new calls but is separate from explicit revocation events. Account-wide cancellation matches current local logout/revocation semantics and may also stop jobs started with another credential for that owner. Verify two real hosted routers with independent pools sharing SQLite: revoke on one, cancel a live HTTP run and long connection on the other, leave a different owner's work active, deny future revoked-token calls, and avoid replaying historical events at startup. PostgreSQL/MySQL deployment and broader matrix/release validation remain deferred to unified verification.
