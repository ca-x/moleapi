# Hosted workspace membership and roles

Status: implementation specification for the first integrated collaboration release, covering `collaboration-002/003/004` and part of `collaboration-001`. Capability boundaries are in `docs/COLLABORATION-CAPABILITY-MAP.md`.

## Objective and assumptions

A hosted workspace owner can invite an existing or future MoleAPI account using a single-use link, assign a role, see active members and revoke access. Members work against the owner's canonical workspace revision; changes are never copied into member-owned documents. Invitations are displayed once for the owner to copy, with optional delivery through separately configured notifications. A standalone offline workspace keeps its current local-only ownership model.

Roles are `owner`, `admin`, `editor`, `viewer`. There is exactly one owner. Admins manage invitations and non-owner members and can edit resources. Editors can edit and execute supported workspace resources. Viewers can browse a safe projection without saved credentials or private response/history data, and cannot invoke request execution, export secrets or change data. Only the owner may delete or transfer the workspace, issue runner credentials, or manage external/public sharing until later policies explicitly delegate those powers.

## Data and consistency

- Add indexed membership and invitation tables across SQLite, PostgreSQL and MySQL. Membership has a unique `(owner_id, workspace_id, member_id)` key, a fresh generation per acceptance, role, revision and timestamps; an index on `member_id` powers cursor-paginated shared-workspace listing. Invitation has random ID, SHA-256 token digest, role, creator, expiry, consumed/revoked state and an owner/workspace key. Tokens are never stored or logged in plaintext. No new role field is embedded in the canonical workspace payload.
- Create, accept, change role and remove member inside owner/workspace-locked transactions. Acceptance rechecks the active workspace, account and token expiry, enforces a 100-member/20-pending-invitation budget and consumes the token atomically. Same-account retry is idempotent; a different account cannot reuse an accepted token. Workspace deletion invalidates invitations and membership in the same transaction.
- Record successful invitation and membership mutations and shared workspace writes in the same transaction as the change. Audit entries contain actor ID, canonical owner/workspace pair, action, optional subject ID, outcome and time; they contain no token, request body or secret value. Owner/admin sessions can list the latest 100 entries. Workspace deletion removes its audit entries in the same transaction so a reused workspace ID cannot expose an older workspace's actor history.
- Each member request resolves the authenticated actor to the canonical owner and current membership. Local in-process admission controls support prompt cancellation, while cross-instance DB generation/revision checks before committing changes or releasing private responses enforce revocation after removal, rejoining or a role change. A member token retains the actor identity for audit; route handlers receive a separate resolved canonical owner. No role may acquire an owner identity by supplying a workspace ID or runner credential.
- Workspace IDs are unique only under an owner today. Shared routes therefore use the explicit pair `/api/owners/{owner_id}/workspaces/{workspace_id}/…`; invitation acceptance and the shared-workspace picker return both IDs. Existing `/api/workspaces/{id}/…` URLs remain owner-scoped for compatibility. A member cannot use a bare ID to select between different owners with the same workspace ID.
- Preserve existing owner-only URLs and payloads. New membership fields and tables are additive; old databases migrate without rewriting workspace JSON. A member-scoped read of the workspace returns a role-labelled projection. Viewer responses screen credentials, private variables, saved Data sources, full exports and response history using the existing conservative privacy machinery; unsupported safe projections fail closed instead of returning raw owner data.

Viewer projection and the shared picker must screen private values copied into display metadata, including workspace, collection, request, environment, example and specification labels and collection/request descriptions. This uses the existing bounded private-value matcher; resource identifiers and references remain stable. Explicit include-secrets backup retains the original values.

## Route permissions

The shared-route policy is explicit and deny by default for non-owners. A table generated from actual Axum routes assigns the minimum role and whether a route returns private data. Initial editor scope includes workspace GET/PUT with CAS, saved request execution, ordinary history/results, collection/scenario operations and Mock editing through the canonical owner. Viewer scope includes projected workspace/document/specification reads and metadata-only status. Membership management requires admin, and cannot alter the owner. Owner-only paths include workspace delete, member role above admin, access tokens, runner credentials, public shares, full backup and account/security settings. Routes outside an explicitly audited table stay owner-only until classified.

Hosted session authentication is required to create/accept invitations and manage roles; personal API tokens may use an existing membership only after the same role check. Agent credentials and anonymous public links never accept invitations. Role changes take effect on the next request and fence in-flight shared execution before it returns a private result. A removed member's open protocol/mock/runner work is cancelled or withheld by current admission and DB checks.

The first shared execution entry point is `POST /api/owners/{owner}/workspaces/{workspace}/run`. Editors and admins run the canonical owner's collection through the existing runner, with the real actor and job ID recorded as a `workspace.run` start event. A concurrent 200 ms membership watcher cancels the request future and its job lease on cross-instance role change/removal; a final membership check withholds private results. A second scoped entry point executes a canonical saved request by request ID; it rejects ad hoc request payloads, checks the workspace revision before execution, records the actor and polls the same membership fence. Viewer execution and owner-scoped bare-ID routes remain denied. Saved SSE/WebSocket sessions have explicit creator-bound member routes and poll role, revision and credential changes; other protocol sessions and async resources still need their own audited fences.

A separate finite draft entry point accepts a complete request and explicit canonical collection ID with the caller's expected workspace revision. It can run an unsaved edit or new request without implicitly saving it. The server validates the request, rejects a request ID already saved under another collection, checks role and revision before dispatch, records the real actor, and fences both membership and workspace revision during execution and before returning private data. Finite HTTP and GraphQL queries/mutations use this path; saved GraphQL subscriptions use the creator-bound member session policy. The client distinguishes draft-send from canonical saved-send and clears delayed output when draft selection or version changes.

Editors and admins can read the canonical owner's saved history, report summaries/detail and report step responses through explicit owner/workspace routes. Each read checks the current role before loading private data and rechecks the membership revision before returning it. Viewers and removed members receive no history or report data. Editors and admins may download a saved report through an explicit owner/workspace route. This export uses the stored privacy projection, the existing bounded formats and language validation, and a final membership-generation check before returning content. An admitted export attempt records the real actor and report ID as `started`, without report content; the final check occurs after that audit write. Report deletion and history clearing remain owner-only until their write policies are audited.

Editors and admins can preview an existing saved Mock example through an explicit owner/workspace/request/example route and read that workspace's Mock call records. Preview checks the canonical saved IDs, records the real actor, polls membership during generation and rechecks it before releasing the response. The hosted client previews only saved examples and discards a delayed response after selection, edit, revision or membership changes. Viewers cannot preview examples or read calls. Editors/admins can also invoke `ANY /api/owners/{owner}/workspaces/{workspace}/mocks/{*path}` to route incoming HTTP requests against canonical saved examples. Admission locks the canonical workspace, records `mock.route` with the real actor and no URI/body/credentials, and reuses the bounded owner matcher and selected-example script engine. Membership and workspace revision are watched during dispatch and checked again immediately before returning. Viewers, foreign/removed members and bare owner routes remain denied. Public Mock share creation stays owner-only until its policy is audited.

The hosted shared editor can add/remove saved examples and edit their name, status, body, response headers, delay, fault percentage/status and per-minute rate limit through the same canonical workspace CAS write. Shared and owned editors reuse the same bounded traffic controls. Unsaved drafts never feed the preview route. Members can edit bounded matching priority, query/header pairs and an optional exact body through the extracted owned matching editor. The extracted script editor is enabled only for an already enabled v2 workspace. Source, data and traffic settings are preserved while these controls change. In v2 HTTP requests, members can select canonical saved datasets with SQL views, choose the view and row/first shape, and edit up to 16 ordered path/query/header parameters using the extracted owned data editor. Explicit data selection clears inline/link Schema and inference while retaining the static body, script, matching and traffic controls. Existing missing references remain selected with an alert rather than silently choosing another dataset/view. Bindings with request parameters disable direct preview and use the scoped matching route. Dataset management remains separate work. The shared page advertises only the member-scoped route, and only for literal HTTP URLs with single-segment path templates. Members can select static or inline JSON Schema sources, edit a bounded JSON object through the shared dialog and enable field-name inference; workspace CAS Save applies the existing server Schema validation. Existing specification links or data bindings remain selected until an explicit source switch. Members can choose a JSON response from the HTTP request's already linked OpenAPI specification. A dedicated editor/admin `POST /api/owners/{owner}/workspaces/{workspace}/mock-schema/validate` locks canonical role/revision admission, records `mock.schema.validate` without source/pointer content, reuses the bounded owner validator and checks membership/revision while waiting and immediately before returning method/status/media metadata. Selection requires a clean saved draft; success updates only link/status/enabled Content-Type and clears incompatible inline/data sources. Edits, selection/tab/account/role or workspace-version changes discard delayed metadata. Unsupported or stale responses retain the existing source until an explicit valid selection or static/inline switch. The dialog is scoped to the current member/credential, owner/workspace, request/example and saved/conflict revision, so a changed context closes uncommitted Schema text. A successful Save adopts canonical server defaults if the draft has not changed since submission, while edits made during the pending save remain dirty and intact.

For saved HTTP requests, the hosted shared editor reuses the owned editor's query/header, body/file, authentication, assertions/extractions, scripts and network controls. Changes are persisted only by the owner/workspace CAS write; canonical saved-request execution is disabled while the draft is dirty. Switching body mode uses the same descriptor conversion as the owned editor. Non-HTTP protocols retain their limited shared view until their dedicated member editor and execution policies are specified.

Shared collection settings use the same controlled name/parent/auth/variable/script fields as the owned dialog. Editors/admins can create a root collection in an empty workspace, add a child folder or edit an existing collection, including inherited authentication, shared variable execution and pre/post scripts. Apply changes only the member draft; Save uses canonical audited CAS. Existing cycle/depth checks apply; concurrent collection metadata changes reject Apply while current requests are retained. Member local variable overrides are excluded, and owned OAuth token managers never mount in this dialog. Account, credential, role, workspace, saved revision or conflict revision changes close an unapplied dialog. Viewers have no collection mutation controls. Shared request actions can duplicate a request with a fresh identity or move it while retaining its full content/ID; a move must preserve every referencing scenario subtree. Editors/admins can stage request deletion or collection-subtree deletion after reviewing a confirmation, then persist through audited shared CAS. Collection deletion moves its Markdown documents to the root without changing their source. Structural scenario roots/steps and query-dataset references are named and must be updated before deletion; no dependent resource is silently removed. Confirmations bind the original collection/request IDs and exact draft contents/name, and cannot retarget even before passive selection effects run. Scope/selection/data/saved/conflict changes dismiss them. Viewers have no actions. Existing shared storage revokes removed requests' public Mock capabilities transactionally; deletion does not grant members public-share management.

Shared saved scenarios use the canonical workspace CAS path. Editor/admin members can create/edit/apply/cancel scenario drafts, select only requests in the scenario collection subtree, edit step order/group/condition/repeat/branch and parallel blocks through the extracted owned fields, and confirm scenario deletion without removing its requests. Apply checks current scenario metadata and references, preserves existing notification IDs and leaves persistence to explicit shared Save; owner notification management never mounts. Account/credential/role/root/saved/conflict changes discard unapplied forms and confirmations. After reference edits are applied, the resource actions inspect the updated draft, so an obsolete request can be deleted in the same valid CAS write. Only saved scenarios for the selected collection can run; unapplied edits and dirty data block execution. Scenario runs use the existing actor-scoped run/creator Stop/report routes, and the panel disables editing/root changes while a run is active. Viewers have no scenario edit or execution controls.

Shared dataset resources use extracted owned metadata/source/query/view fields. Editors/admins create/edit/apply/cancel datasets, preview literal CSV/JSON and confirm dataset deletion through the member workspace draft and explicit CAS Save. A member-only `POST /api/owners/{owner}/workspaces/{workspace}/dataset/preview` admits the canonical role/revision, records `dataset.preview` without source, reuses bounded parsing and rechecks membership/revision before returning rows. The existing 20-dataset/20-view, 1 MiB per literal source/4 MiB aggregate and read-only SQL rules remain authoritative. Data query sources select a current read-only request ID and force privacy without copying its SQL or credentials. Omitted source/view SQL survives metadata edits. Named Mock bindings prevent dataset deletion or removal of a referenced view until those bindings are explicitly changed. Unapplied fields and delayed validation are fenced by account/credential/saved/conflict scope, exact edit identity and current canonical query-cache revision, including cache updates before React notification. Owner-only preview/resource URLs are not used. Shared Data request creation/editing and saved sessions are described below; remaining protocol/specification parity is still required.

OAuth1/OAuth2 configuration can be inspected and edited in the shared request, but private token management controls remain owner-only. The owned editor's token managers use the active owned workspace context and must not mount inside a member's shared view; member-scoped token vault operations require separate explicit routes and actor policy.

A successful shared preview carries `x-moleapi-mock-preview: saved-example`, regardless of its simulated HTTP status. The client treats an unmarked status as an API/auth error, so an intentional saved 401 does not expire the member's session and a denied 403/404 cannot appear as example content.

Shared Markdown documents use the canonical workspace CAS data path. Viewers see only the already screened workspace projection and can safely preview its nonprivate sources; editors/admins can create, edit, move, mark backup privacy, preview and remove documents in a local draft before saving. The same document validation gates every member Save entry point. Internal request links can select only a request in the same projected workspace. Public document publication and password/appearance controls remain owner-only.

Shared project, collection and environment variables also use the canonical workspace CAS data path. Viewers see only the privacy-projected values. Editors/admins can edit shared rows and create, rename, select and remove environments; a deletion needs confirmation and remains a draft until Save. Member local overrides and owned variable-file routes are separate account state and do not appear in this editor. This does not introduce a team-level variable scope.

## Client behavior

Shared collection runs expose `POST /api/owners/{owner}/workspaces/{workspace}/run/cancel` to an editor/admin who created the run. The client sends the original `job_id`; the server derives a distinct internal key from owner/workspace, actor, membership generation/revision and that ID. Another member's identical ID cannot stop the creator's run. Viewers and removed members are denied. Cancellation checks current membership under the workspace lock, audits the real actor as `workspace.run.cancel` with `requested` outcome, and signals the existing runner cancellation token. Bounded early cancellation supports Stop arriving before execution registration; the result retains the original client ID and a saved cancelled report. The shared view offers a bilingual Stop action and ignores late responses after scope changes. One workspace-level active-run region identifies the original collection/scenario and exposes creator Stop on every shared page, even after selecting or deleting its collection. Local edits, Save, selection and remote revisions invalidate inline output without dropping the active job; another run remains blocked until the original promise actually settles. Completion and Stop callbacks compare exact job identity, and Stop acknowledgment alone does not mark execution complete. Same-scope successful completion refreshes history/reports even when its inline result is obsolete. Account/credential/role/owner/workspace changes still discard the old job UI and fence all callbacks. The in-process cancellation registry requires the request to reach the executing server instance; durable distributed job routing remains separate work.

- Workspace picker lists owned and shared workspaces with role and owner label, without duplicating IDs across owners. Account switch/logout closes member-scoped drafts, query caches, pending saves and protocol sessions.
- Member management offers labelled role selection, single-use link copy, expiry/revoke controls and member removal confirmation. It never shows stored token digests. Editors see edit/run controls but no management buttons; viewers see a clear read-only state and no write/run action. The server remains authoritative if a stale client invokes a forbidden action.
- Sync and offline behavior remain explicit: a shared hosted workspace may be cached only within the member's authenticated account scope. Offline edits to a shared workspace are not silently accepted; reconcile with current membership and revision before upload, showing conflicts and revoked access. Local offline workspaces cannot be invited until migrated to hosted ownership through the existing explicit sync flow.

Existing runner agent scopes and anonymous public routes remain separate principals.

## Outside this integrated slice

Organization/team hierarchies, project-specific custom ACLs, realtime presence, comments, user groups, SSO/SCIM, domain capture, BYOK and cross-organization partner workspaces remain separate matrix work. This specification does not mark the complete collaboration or administration modules finished.

### Shared dataset-driven collection and scenario runs

Editors/admins share one workspace-scoped local run configuration across Resources and Scenarios: no dataset by default, an explicitly selected saved dataset, or temporary CSV/JSON, plus automatic or 1–100 iterations. Saved selections send only dataset_id; query-backed selections are valid without literal source and refresh in the canonical owner runner. Missing/deleted sources remain explicitly selected and block execution. Temporary data never enters workspace CAS and uses member preview with expected_revision. Actor/credential/role/owner/workspace changes immediately reset effective options; tab changes preserve input. Actual jobs lock options and retain the global Stop control. Dispatch checks the current query-cache revision before resolving options against saved data.

### Shared Data request and session management

Editors/admins can add a Data request, edit its PostgreSQL/MySQL/local-file/remote-file source settings, bounded file formats and worksheet/table options, URL, SQL, TLS/CA, authentication, request/query scripts, assertions and extractions, then Save through shared canonical CAS. Local file imports preserve later SQL edits and discard delayed results after source identity or member/cache/conflict boundaries change. No owner token manager mounts. Viewers have no Data mutation or connection controls.

Saved Data sessions reuse the member creator/revision/credential fencing and existing Data query preparation/postprocessing. The member send route admits only query, schema refresh and cancellation for Data; WebSocket message rules remain separate. Source/script edits close the old connection and require Save/reconnect. Session SQL is temporary, supports cursor/selection execution, formatting/completion, Schema browsing/search, result sorting/search/pagination and CSV/JSON export. Query/schema/cancel admission records actor-only metadata without SQL/source. File rows remain live-only in history. Data completion carries actor credential/revision checks; shared history insertion and role/revision admission use the same canonical workspace row lock and database transaction as member changes, so a waiting completion cannot write after a committed demotion. Results are rechecked before release. Remaining specification/protocol parity and native acceptance remain required work.

### Shared query result snapshots

A completed shared Data result can be saved as a private canonical JSON dataset through member preview and workspace CAS at the admitted saved revision. All returned rows are snapshotted independently of result-table filtering/sorting/pagination; integer/decimal strings retain exact precision, booleans and null retain type. The shared converter rejects failed/incomplete/truncated/empty results, binary/capped cells, ambiguous columns and existing 100-row/100-column/1 MiB source limits; creation validates UTF-8 name bytes, 20 datasets and 4 MiB aggregate. The member path uses no owner-only route and sends no SQL or connection metadata in the dataset.

The dialog binds the exact query result and inherits session/member/credential/workspace/revision scope. A changed or closed result or newer cached canonical revision prevents a delayed preview from dispatching CAS. Clean saved data is required. Network failure retains the name and same candidate ID for retry; a later workspace refetch can reconcile an already committed write whose response was lost. Success requires the canonical response to confirm dataset ID, name, privacy, source and newer revision. Local edits made during an in-flight PUT survive response adoption and retain the newly persisted dataset. The resulting dataset is immediately selectable for shared runs; adding its ordinary read-only view enables existing Mock binding.

### Shared specification resources

Viewers browse privacy-projected retained sources without mutation controls. Editors/admins import OpenAPI 3.0/3.1 JSON/YAML, optionally append generated requests and environments, update OpenAPI source, rename retained specification metadata and delete unreferenced specifications through an explicit shared workspace CAS Save. The current environment never changes during import; it must be explicitly selected before executing generated requests that use imported variables. New sources/IDs/request associations are preserved, and OpenAPI source replacement retains the original specification ID and all authored collections/requests/environments. Other source kinds remain read-only in this panel while their metadata/removal is supported; dedicated source editors/source-bundle and remaining protocol parity remain required work.

`POST /api/owners/{owner}/workspaces/{workspace}/specifications/preview` admits editor/admin against the canonical saved revision, bounds the title/source, records specification.preview without source content, reuses the existing OpenAPI importer, merges the candidate with canonical data and validates the whole workspace. A membership/version watcher fences asynchronous work. Credential validation precedes the final member/version read; no subsequent async credential check may release a now-stale candidate. Source import/replace require a clean saved client draft, and staged preview does not persist. File/preview results are fenced by exact edit identity, account/credential/role/workspace/conflict scope and authoritative query-cache revision, including pre-notification updates.

HTTP request association is an explicit OpenAPI selection, preserves request content and clears only an obsolete operation ID. Existing missing/non-OpenAPI associations remain explicit. Linked Mock examples must be cleared before switching the request association. Request and Mock references are named before specification removal, block confirmation until explicitly updated and are never silently deleted. Confirm binds the original specification ID/data. The canonical validator rejects source updates that invalidate existing linked Mock responses.

### Monitored-operation resource lifetime

Membership/revision watchers and operation futures must be destroyed before the final authorization read is polled. Borrowing pinned futures in a select does not drop the losing future when the select expression returns; a retained database query can occupy the pool connection required by the final check. All seven monitored shared endpoints use a common owned boundary with an inner scope for both raced futures. Revocation keeps priority and exact job cancellation, and final permission checks still fence successful and failed operation output. Scheduled execution applies the same lifetime rule before persisting its occurrence. The reproducible pool-starvation diagnosis and scoped tests are recorded in `docs/diagnostics/shared-watcher-pool-starvation.md`.

### Shared GraphQL workbench

Editors/admins create and configure GraphQL requests using the same controlled GraphiQL Monaco editor as the owned workbench. Actual editor document, variables and AST-selected operation execute through the member finite draft route, preserving request headers, inherited authentication, assertions, scripts and network settings. No GraphiQL browser history or member-local overrides are persisted.

Canonical Schema introspection and saved request-linked schema loading have explicit actor-audited member routes with expected revision, credential and membership fences. Introspection returns a candidate; attaching the returned specification and request link changes only the member draft until explicit workspace CAS Save. Delayed replies and disposed editor callbacks are fenced by mounted state, selected request, exact draft, account/credential/role/workspace and authoritative cache revision.

Subscriptions require a clean saved request whose document, selected operation and parsed variables match the actual editor operation. Connection URL and bounded JSON-object parameters are staged then saved. Creation, event polling and Stop use member creator/revision/credential-bound sessions. Dirty edits cannot open a new subscription; leaving scope closes known sessions with the original credential and suppresses late output. Response variable updates do not silently write canonical workspace data. Viewers have no GraphQL execution/configuration controls.

### Shared SSE and WebSocket authoring

Editors/admins create new SSE or WebSocket requests with fresh IDs, edit name/URL/description, query/header/auth, request-before scripts and connection/network settings, and Save through canonical shared CAS. Both use GET and no body as required by the existing live-protocol validator; WebSocket uses HTTP1. Body/assertion controls are excluded for both, and existing response scripts remain explicitly visible for removal because live connections reject them. No owned token/cookie management or local overrides are mounted. New or edited requests require Save before connecting.

The authorized creator-bound session exposes the same URL/status/header handshake projection as the owned workbench alongside its existing bounded events and WebSocket text/binary/Ping controls. Revocation, account/credential/role/selection/saved revision and newer authoritative cache changes prevent stale live operations/results; scope cleanup closes the original session with the original credential. Late network certificate reads bind the original request and settings snapshot.

### Shared TCP client

Editors/admins create TCP requests, configure the existing framing/encoding/private-message/network/TLS/timeout/idle/frame-size/Nagle fields and pre-scripts, then explicitly Save the canonical source before connecting. The shared saved TCP session uses the existing canonical owner environment/pre-script snapshot and codec/privacy limits from tcp-client.md. No HTTP body/auth/header/query/handshake controls or owned managers are mounted.

While connected, a separate session-local message draft starts from the saved template and supports explicit text/Hex/Base64 send and secret marking. Editing/sending it does not change canonical source or workspace revision. Half-close requires a named confirmation bound to that exact session and current member/cache/credential context; it closes only the send side and retains incoming events. Closed/half-closed sessions cannot send. New source edits require Save/reconnect, and scope/revision/role/credential invalidation closes or withholds the original session. Member TCP admission/send/half-close audits contain action/actor/session only, never payload. Viewers have no TCP authoring/connection/send controls.

### Shared Socket.IO client

Editors/admins author Socket.IO namespace/Engine.IO path/Auth JSON, initial listener names, event/JSON/binary/ACK template and common query/header/auth/pre-script/network settings, then explicitly Save canonical configuration before connecting. Saved source and incomplete drafts retain existing Socket.IO validation rules and bounds. The existing mature WebSocket-only SDK handles protocol frames, heartbeat and ACK identifiers; native WebSocket text sends are not Socket.IO commands.

A creator-bound shared session starts from the owner's canonical saved configuration/environment snapshot. A separate session-local event/listener draft supports explicit named JSON/binary emit, outgoing ACK/timeout results, runtime listen/unlisten and single-use incoming ACK replies. These live controls never automatically mutate canonical source. Namespace/path/Auth remain connection settings requiring Save/reconnect. Current actor/credential/role/cache/request/revision and mounted/session/callback identities fence late commands/results; source updates merge the latest config without overwriting concurrent fields. Successful ACK acceptance consumes its callback even if its dialog was dismissed.

Member Socket.IO routes admit only saved Socket.IO sessions and typed emit/listen/ACK commands with creator/member/revision/credential checks. Audit stores action/actor/session only, no event name, arguments, binary data or ACK token. Viewers cannot configure/connect/send or see private events. Existing session limits/privacy/revocation/cleanup and explicit unsupported-protocol rules remain authoritative.

### Shared gRPC client

Editors/admins create and configure gRPC requests, import bounded virtual multi-file Proto sources or perform canonical saved Server Reflection, browse linked definitions/services/methods/templates and explicitly CAS Save staged specification/request references. Import/Reflection never auto-save the workspace or apply response variable updates. Schema loading binds the saved request association; authored definitions preserve their original proto/descriptor representation. Member routes use request_id and expected_revision, canonical owner resources, authenticated actor credentials, actor-only audit, membership/revision/credential watching and a credential-then-final-member release fence.

Saved member sessions support unary, server-streaming, client-streaming and bidi through the existing mature codec/transport. The canonical saved message supplies the first message. A separate local message editor supports further client/bidi messages, explicit half-close and Stop without persisting those edits. Status/metadata/trailers/messages retain existing bounded event/privacy rules; no HTTP handshake is fabricated. Wrong method modes, closed/half-closed sessions and other creators cannot send.

Source callbacks, files, compiled candidates, Reflection and stream completion bind mounted actor/credential/role/cache/revision/request/draft context. Dirty or conflicting work requires explicit Save before canonical source operations/connections. Shared code never mounts owned context hooks/token managers or member-local overrides. Viewers have no authoring/connection/execution controls. Existing unsupported event scripts and native installed/integrated release gates remain explicit.

### Shared MQTT client

Editors/admins create and edit MQTT3.1.1/5 requests with connection/session/reconnect settings, message topic/payload/encoding/QoS/retain/properties, named saved messages, subscription filters/options/properties, Will and common supported auth/network/TLS/pre-script controls. Changes stage in the shared draft and require explicit CAS Save. Saved request/revision member Connect resolves canonical owner variables/resources with no member-local overrides; viewer/foreign/creator/member/revision/credential fences apply to all private session operations.

Shared runtime reuses controlled MQTT message/subscription/event/telemetry controls on a session-local config initialized from the saved source. Publish and subscribe/unsubscribe changes never implicitly save the canonical request or saved-message resources. Connection/Will/network mutation and named-message add/update/delete are absent at runtime; saved-message load remains local. MQTT commands are exactly publish/subscribe/unsubscribe/abort, with content-free actor audits. Graceful Stop sends DISCONNECT; explicit confirmed Abort retains actual Broker Will semantics. Delayed subscriptions, editor callbacks and Abort confirmations bind exact mounted scope/session/current authorization so they cannot target a changed account/credential/role/cache/revision/request. Saved MQTT5 options remain version-guarded. Existing limits/privacy/rumqttc network policy and final native/platform acceptance requirements remain.

### Shared SOAP client

Editors/admins create SOAP1.1/1.2 requests, stage original multi-file WSDL/XSD or explicit checked URL candidates, inspect service/port/operation metadata, adopt endpoint/action/version and explicitly generate or confirm replacement of an editable XML template. Candidates and request associations require explicit canonical CAS Save; source operations bind a saved SOAP request and revision, linked schema reads bind its saved association.
