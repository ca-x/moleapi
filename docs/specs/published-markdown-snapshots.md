# Published Markdown snapshots

Authority: `documentation-004`, `documentation-005`, `documentation-006` and `documentation-014` in `docs/FEATURE-MATRIX.md`, the private workspace documents in `markdown-document-resources.md`, and the existing hosted owner/session contract. This is the first hosted publication profile; it does not claim complete documentation-site parity.

## Objective and assumptions

An authenticated workspace owner can deliberately publish a fixed selection of saved, nonsecret Markdown documents and hand out a public URL. Readers see exactly the selected snapshot until its owner revokes it. Workspace edits, sync, restore and deletion never silently republish content. Publishing is hosted-only; an offline desktop workspace has no public URL.

The first profile publishes authored Markdown, title and folder label only. It excludes saved requests, generated API reference, credentials, private documents, attached files and runtime data. A `moleapi:` link remains inert in a public snapshot; ordinary HTTP(S)/mailto links use the existing safe renderer. Future API-reference publication needs its own explicit field-level disclosure contract.

## Snapshot and access contract

- `POST /api/workspaces/{id}/doc-publications` supplies a visible site title (1–128 characters), `expected_revision`, 1–32 distinct document IDs and a client-generated idempotency key (1–128 bytes). Every selected document must exist and have `secret=false`. Reject unsaved revisions, empty selection, duplicates, private documents and missing IDs atomically. Reusing a key with different content returns conflict. The owner sees a plain warning that chosen source becomes readable without login.
- The server creates an immutable snapshot of selected IDs, titles, folder labels and exact Markdown source from the saved revision. The total source is at most 1 MiB. A 128-bit or stronger random URL identifier is generated by the server. The public URL is `/docs/{id}`; `GET /api/public/docs/{id}` returns the bounded snapshot without workspace, owner, revision internals or credentials.
- Each publish creates one separately revocable version. `GET /api/workspaces/{id}/doc-publications` lists the owner's versions with creation time, source workspace revision, selected titles, revocation state and public URL, newest first; `DELETE /api/workspaces/{id}/doc-publications/{publication}` revokes one. Limit active versions to 20 and retained versions to 256 per workspace. A retry with the same idempotency key and content returns the same active version; a revoked version remains a tombstone and its old key returns conflict, so retries cannot republish it. Old active versions remain unchanged after a new publish until explicitly revoked.
- Revoke and workspace deletion remove public access. A revoked, unknown, malformed or wrong-kind ID returns the same generic 404. Public reads consult shared database state on every request so revocation works across instances; storage errors fail closed. No process cache of public payloads or publication validity.
- Hosted session ownership is required for create/list/revoke. A bearer API token alone does not authorize publication. Local IPC may preview the saved source but cannot publish. Publication metadata and content are excluded from workspace backup/sync and are not recreated by restore.
- Public JSON and HTML responses use `Cache-Control: no-store`, `Referrer-Policy: no-referrer`, `X-Content-Type-Options: nosniff` and a restrictive content security policy. No token, account, source workspace ID, private paths or query text is written to response diagnostics or logs. Public rendering performs no network fetch and never executes HTML from Markdown.

## Product behavior

- The Documents page has a bilingual publication panel for saved hosted workspaces. It lists eligible nonsecret documents, requires a deliberate selection and confirmation, and shows the exact selected titles plus a public-content warning before submit. A dirty draft must be saved first; the submitted revision is checked by the server.
- After creation the owner can copy/open the public URL, list prior versions and revoke each one. No private source or unselected document appears in this list. The panel explains that workspace edits do not update old publications.
- The public page uses the same safe Markdown renderer, with a clear site title, document navigation and empty/error state at 390 px and desktop widths. Public UI has no account/workspace controls, request runner, editor or internal request-link action. Its fetch uses only the public endpoint and does not send credentials.

## Verification

- Core/server tests cover selection limits, saved revision mismatch, private/missing documents, immutable versions, idempotent retry, concurrent create limit, owner boundaries, revocation across two app instances, workspace deletion, backup omission and generic 404 behavior on SQLite, PostgreSQL and MySQL.
- A real hosted browser publishes a nonsecret document beside a private document containing a sentinel, reads the public URL anonymously at 390 px, verifies no sentinel/HTML execution/remote image request, edits the source and confirms the old version remains fixed, then revokes and receives 404. English and Chinese owner controls and keyboard operation are checked.
- Run `cargo test -p moleapi-server --test published_docs`, relevant core/formats tests, `npm --prefix web test -- --run`, `npm --prefix web run build`, strict scoped Clippy, `cargo fmt -- --check`, embedded server build, three-database CI, Docker and fixed-head native packages. Installed-package smoke remains a separate release gate.

## Structure and boundaries

Use a dedicated `doc-publication` kind in the existing `documents` table, with database transactions and workspace-row locking for create/revoke/limit enforcement. Keep public routing separate from authenticated workspace routes. Do not store publication IDs or snapshots inside `WorkspaceData`; that avoids sync/backup copying public grants. Keep public rendering in a standalone frontend entry/page that cannot load the private application state.

Do not claim password sharing, custom domains, published API request examples, online debugging, site analytics, custom CSS/JS, native hosting or complete `documentation-004`–`006` support from this profile. Those remain in the 395-item target.
