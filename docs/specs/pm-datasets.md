# Query workspace datasets from scripts

Authority: `data-009` and `data-010` in `docs/FEATURE-MATRIX.md`, `docs/specs/saved-datasets.md`, `docs/specs/data-driven-runner.md`, and Postman v12's [dataset query guide](https://learning.postman.com/docs/tests-and-scripts/datasets/query-datasets-in-scripts) and [`pm.datasets` reference](https://learning.postman.com/docs/tests-and-scripts/write-scripts/postman-sandbox-reference/pm-datasets/). The public reference defines `pm.datasets(id)`, asynchronous `executeQuery(sql, params?)` and `executeView(viewId, params?)`, and an async iterable `result.rows`. A dataset ID is the authority; a display name alone does not select a dataset.

## Capability order

1. `script-async` (scripts module): bounded top-level `await` and Promise job draining in the existing isolated QuickJS worker. This must retain the current memory, CPU, wall-clock, cancellation and private-value gates. Detached or never-settling jobs cannot mutate output after a phase is returned.
2. `dataset-script-query` (data + scripts modules): owner/workspace-revision snapshots of saved dataset rows, an in-memory read-only SQL engine, bound `?` parameters, and `pm.datasets(id).executeQuery` with async iterable rows. It works in pre-request and post-response scripts for interactive, collection, scheduled, CLI and agent runs. No script-controlled filesystem or network access is added.
3. `dataset-script-views` (data + workbench modules): bounded saved view IDs/SQL per dataset, CAS editing, default/full backup behavior and `executeView`. Old workspaces retain their existing sources and default to no views.
4. `dataset-script-live-and-mock` (data + Mock modules): query-backed datasets require an on-demand checked host bridge, and dynamic mock implementations require a Mock script execution contract. Both use the same public `pm.datasets` shape, with owner/revision/cancellation/privacy tests. They remain open until those separate gates pass; completing the first three capabilities alone does not close the full Data/Mock matrix rows.

## Script contract and budgets

- Allow top-level `await` only in the versioned `moleapi-pm/2` script mode. Existing `moleapi-pm/1` scripts keep their rejection of Promise creation and detached jobs. A workspace opts all of its scripts into v2 explicitly; old saved workspaces retain v1 semantics. Within v2, run each phase to a settled result before exporting request mutations, logs, tests or variable updates. Reject unresolved/rejected jobs and attempts to leave work running after the phase. Existing one-process-per-phase kill/reap remains the absolute backstop.
- A script loads only a saved dataset in its owned workspace by ID. Missing, redacted, foreign or changed references reject before returning rows. An explicit `{{variable}}` in a request may resolve to the saved ID using existing interpolation; `pm.datasets` itself does not search by name or fetch URLs.
- For literal CSV/JSON sources, the host parses the saved source once at the start of an execution phase and sends bounded immutable rows to the worker. At most 20 datasets, the existing 4 MiB aggregate saved-source cap, 100 rows and 100 columns per dataset, and the existing script IPC/memory limits remain authoritative. If snapshots cannot fit, fail the phase before user code; never silently omit datasets. Query-backed sources need the later on-demand host bridge and must produce an explicit unsupported-source error until it is implemented.
- A dataset has a stable SQL table name: an additive validated `table_name` field, defaulting to `data` for old datasets. Only one saved source table is available per handle. `executeQuery` and saved views accept one read-only SELECT/CTE statement up to 64 KiB, at most 64 positional string parameters, and no file extension/attachment or independent network. Use a mature SQLite library with prepared bindings, an operation progress budget and the existing worker deadline. Reject multiple statements, DDL/DML/PRAGMA writes, oversized/unsupported cells, more than 100 rows/columns or 1 MiB serialized result. Return exact 64-bit integers/decimals as strings and preserve null/boolean/text types.
- Results expose `{ rows }`, where `rows` implements `Symbol.asyncIterator` and yields detached copies of row objects. An exhausted iterator does not reveal more rows. Query errors reject the returned Promise; scripts may catch them, but private dataset values and query diagnostics remain screened in logs, reports, history and default backups. Parameter binding must never interpolate into SQL text.
- `executeView(id, params)` resolves a saved view by ID from the selected dataset and executes its stored read-only SQL with the same budget and row contract. View IDs are unique within a dataset. Default backup withholds private source/view values according to existing dataset privacy, while full MoleAPI backup restores exact authored text. Other export formats continue rejecting saved datasets.

## Files and verification

Rust model/validation lives in `crates/core/src/datasets.rs`; the in-memory query adapter belongs in the existing data/script runtime packages, using a mature SQL engine rather than an application parser. QuickJS API lives in `crates/script-runtime/src/pm.js` and the worker protocol. Hosted/native/CLI execution uses the existing shared server path. The React saved-dataset editor owns table and view controls; bilingual catalog entries and 390px layouts are required.

The SQL adapter pins `rusqlite 0.32.1` (MIT; [source](https://github.com/rusqlite/rusqlite), [crate](https://crates.io/crates/rusqlite/0.32.1)) with its bundled public-domain SQLite C library and `sqlparser 0.63.0` (Apache-2.0; [source](https://github.com/apache/datafusion-sqlparser-rs)). These are build-time dependencies; execution never downloads a SQL engine.

Tests must cover v1 backward compatibility, v2 top-level await, settled/rejected/pending and detached promises, worker kill/reap, owner/revision changes, CSV/JSON typed rows, SQL injection attempts with bound parameters, readonly/multi-statement rejection, row/byte/CPU limits, async iteration, saved view CRUD, default/full backup privacy, real pre/post scripts against a loopback request, scheduled/CLI/agent runs, and 390px English/Chinese UI. Run focused Rust/frontend tests, strict Clippy and builds, then the configured three-database and native platform gates. The current static Mock route is not evidence of mock-script support.

## Implementation boundaries

- Always reuse workspace owner/CAS and existing cancellation; never expose server paths, raw credential URLs or unbounded rows to QuickJS.
- New dependencies must have pinned versions and source/license records; no remote script or SQL engine download at runtime.
- Preserve old v1 behavior and explicit unsupported cases until the matching capability has real tests. Do not advertise the full `pm.datasets` contract from a partial script-only implementation.
