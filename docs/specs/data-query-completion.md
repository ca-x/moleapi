# Data query completion, scripts and history

Authority: remaining-work milestone 3, feature matrix `protocols-017` and `data-001`–`data-010`, `data-client.md`, and the existing shared script/history contracts. Data's live SQL session currently emits volatile columns/rows/finished events; finishing a query does not run response assertions, extractions or post scripts, and no Data result enters durable workspace history.

## Capability map

1. **Completion delivery (`data-completion`)**: after each Data query reaches a terminal outcome, the protocol runtime sends one bounded typed completion to its server owner. The existing live events remain immediate and authoritative for the SQL operation. Backpressure or a vanished consumer yields an explicit postprocessing error event; it never retries SQL or changes a successful query into a claimed rollback.
2. **Shared postprocessing (`data-postprocess`)**: the server converts a successful typed result into a versioned JSON response view and runs the existing response assertions, extraction worker and post-response scripts with the saved request/collection/workspace chain and scoped variable snapshot. It exposes per-query tests/logs/variable updates in a session event, fenced to the same account/workspace/request/session. A failed or incomplete-privacy script withholds history values as the ordinary execute route does. Pre-request scripts currently run at connection establishment; per-query pre-script execution and SQL mutation are a separate required continuation, not implied by this response slice.
3. **Durable history (`data-history`)**: each terminal query outcome produces at most one owner/workspace-scoped history record after a final owner/session/admission check. It retains the actual query ID, resolved SQL source, typed columns/rows or error/cancellation outcome, row counts, truncation and elapsed time in a versioned response body. Preserve existing known-secret screening. File-backed query rows are withheld by default because selected/downloaded file contents can be private; record their outcome and schema metadata. Database result bodies exceeding the script/history body budget are withheld with a clear reason, while the live Data event stream still shows its original bounded result. The history page can open the record without treating Data as HTTP, and the Data workbench shows the history ID or a postprocessing error.

## Contract and limits

- No new application database table. Reuse existing `history` documents, owner key and workspace reference. The current 100-entry retrieval and clear-history semantics apply. An old workspace and existing history records retain their shape.
- `DataCompletion` carries `query_id`, SQL source and a success/error/cancelled typed outcome through a bounded per-session channel. The protocol runtime must not depend on storage or scripts. Server postprocessing may lag query completion but cannot silently disappear: it emits a `data_processed` or `data_postprocess_error` event associated with that query ID.
- A success response has status 200, `status_text="Data query"`, `content-type: application/vnd.moleapi.data+json`, and JSON body `format=moleapi-data-result-v1` with typed rows, columns, SQL, rows affected and truncation. Errors/cancellation use distinct status/reason; cancelled writes say their outcome may be unknown. No SQL retry occurs. The response is a view of an already-completed query, never a second execution.
- The post-script worker's 5 MiB body limit and history document budget are authoritative. If the serialized response would exceed 5 MiB, skip response scripts/extractions with an explicit event and persist metadata-only history; never silently pass a partial result to an assertion. The existing Data live row/result caps continue independently.
- The completion consumer holds only bounded results. It stops on logout/session removal/workspace deletion or a changed admission generation, checks ownership again before history insertion, and never applies variable updates to another account or a stale workspace. Script/extraction updates remain scoped and are returned as live event data for the current editor; canonical saved drafts are not silently mutated.

## Evidence

Real local file and hosted PostgreSQL/MySQL query fixtures must prove success, error, cancellation and a write with no replay; scripts/assertions/extractions see the typed JSON result only once. Check exact owner isolation, logout/deletion fencing, private known values, file-row withholding, oversized result behavior, storage restoration and history clear. The bilingual 390px workbench must show postprocessing status and open a saved Data history record. Source tests, three-database CI, native/hosted parity and platform packaging remain separate gates. This capability does not complete per-query pre scripts, query-produced saved datasets, legacy Spreadsheet formats, EDAS or the full product goal.
