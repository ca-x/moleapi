# Interactive/scenario/CI completion notifications

Extend the existing notification engine to ordinary owned collection/scenario runs and API-driven CI. Saved scenarios add default-empty notification_ids; requests may omit IDs to inherit that list or explicitly supply IDs/empty list. Validate unique bounded IDs and owned workspace targets before sending any request. Label run_origin as interactive or ci; this is a caller-supplied event label, not an authority/permission claim. Scheduled invocation explicitly suppresses this binding to prevent duplicate scheduled plus ordinary events.

Publish completion/cancel/failed-flow events in the same transaction as a successful saved report. Failed report persistence or stale/deleted owner/workspace must not acknowledge an event referencing an unavailable report. Reuse the owned durable outbox, all existing provider transports, privacy projection, receipt handling and retries. Distinguish RUN_COMPLETED/CI_RUN_COMPLETED/SCHEDULE_RUN_COMPLETED event kinds; prior schedule deliveries retain default kind compatibility. Maintain resource/origin-scoped outcome state for change-only rules and preserve stable provider dedup identities. No live credential/body/variable values in event data.

Bilingual testing controls select per-run targets or saved scenario defaults; saved scenario editing preserves notification references across CAS/sync. Missing references from another instance fail explicitly before transport. Scheduled definitions keep independent targets. Necessary actual API cases cover inherited/manual-empty/CI labels/privacy, wrong-owner target prevalidation without request delivery, stopped runs, and no duplicate scheduled notification; scoped UI/catalog/type/build only. Workspace collaboration event subscriptions, other integrations/distributed runners and the remaining release goal stay open.
