# Parallel scenario blocks

Add persisted named parallel blocks to scenarios: stable ID/name,2–8 consecutive enabled member step IDs and1–4 concurrency. A step belongs to at most one block. External declarative/script jumps may enter only the first member; member graph successors are unsupported in this initial block model and must reject at save rather than silently lose their meaning. Conditions and per-member repeats remain supported; nested/multi-step branch graphs remain subsequent required scope.

Use futures-util/Tokio, the existing finite request executor and snapshot VariableScopes. Each member owns an isolated scope fork. Repetitions execute in bounded rounds; branches retain their own variables/prior response and never see peer writes. A false condition ends that member's repetitions. Each launch consumes the existing global1000-step quota and shares the run cancellation/deadline/owner fences. Peer results are ordered by saved member order per round, independent of network completion order. Scripts cannot redirect shared flow from a peer; explicit script controls produce a fixed parallel_control error and stop the block. Request failures remain real failed results.

History is deferred for a parallel batch until all its completed members' private taints are available, using the exact prepared request/environment and existing history privacy machinery. Hold at most eight bounded response/request objects per round, not all repeat responses. Record no skipped request history. Await/drop cancellation kills outstanding child work; do not fake transport rollback.

At join, merge final write intents by namespace and key. Identical values agree; differing values/deletion conflict stops with parallel_variable_conflict and applies no shared updates from the block. Collection namespaces use the selected collection IDs. Preserve per-branch taints, enforce total variable/overlay budgets and apply approved updates atomically. Mark peer response setters as unapplied to browser-local state; return final approved parallel updates once, adjusted for any subsequent sequential updates, so the client does not invent completion-order last-write-wins. Shared canonical workspace data remains unchanged.

The bilingual Radix editor selects contiguous member ranges, names/concurrency, removes blocks explicitly and displays membership. Edits to step order/enabled/member controls must be validated; do not silently dissolve blocks. Runner reports identify blocks and show fixed condition/control/conflict stops. Additive defaults preserve old scenarios. Default backups screen names; privacy-disabled members remove them from blocks, dropping blocks with fewer than two safe members so backups remain importable. Explicit backups retain exact blocks. Old-server source-loss sync refusal applies.

Necessary checks: actual simultaneous HTTP requests with a synchronization barrier, independent branch inputs/repeats/conditions, deterministic report ordering, approved updates available to the next sequential request, same-value agreement/different-value/deletion conflict, per-collection namespace isolation, cross-peer history taints, cancellation/owner isolation and invalid membership/edge saves. Scoped UI/catalog/type/build and execution/history regressions only. Full matrix, final unified review, main merge and Actions release remain the goal.
