# Scenario branching and loop coverage

Saved request steps now have optional condition, repeat, on_true and on_false controls. Conditions are JavaScript expressions evaluated by the existing mature QuickJS runtime in the application script worker. No separate expression parser/VM is introduced. The host reads a synchronous boolean directly from the evaluated JS value; serialized script output cannot substitute its result. Promise work, nonbooleans, exceptions, allocation/deadline failures and malformed syntax fail the run with a fixed condition_error diagnostic, without returning expression/private text.

## Execution semantics

Conditions run before all request pre-scripts against snapshot pm variables, typed dataset/iteration metadata, the selected saved request and the previous actual response within the current data iteration. Condition-generated variable/request changes, execution controls, tests and logs are discarded; privacy taints are retained. False means no request pre/post scripts, transport or request history. The report marks condition_skipped. Evaluation failure reports one failed step and stops the run. Owner/workspace admission is checked again after the condition worker yields; cancellation/deadline selection also covers evaluation itself.

True means ordinary request execution. Script next-request/stop controls take precedence over declarative controls. Otherwise the request repeats up to its repeat count, re-evaluating its condition before each visit, then follows on_true. False follows on_false immediately. An omitted target advances to the next enabled step; typed targets select an exact enabled step ID or end the current data iteration. Explicit backwards edges form multi-step loops. Their counters reset on a jump, and every visit—including false/skipped visits—consumes the existing1000-step budget. Dataset iterations continue after a declarative stop, recorded separately as scenario_stopped. Request IDs/names remain subject to existing unique-occurrence script-jump rules.

Conditions are capped at4KiB and repeats at1–1000. Nominal enabled repeats times dataset iterations cannot exceed1000; dynamic branches/cycles retain the execution limit. The existing250ms VM/64MiB/512KiB stack/1s application-child,300s run, capacity and report bounds apply. References to missing steps or enabled edges to disabled targets reject saves. The editor uses Radix textarea/number/choice controls with bilingual descriptions, exact stable target IDs and no added motion on frequent editing. Reordering does not rewrite branch identity. Deleting/disabling a target explicitly ends incoming branches; the UI describes this behavior.

Default backups remove and disable condition text changed by credential screening, redirecting its incoming branches to end the iteration so the backup remains importable. Explicit backups preserve conditions/repeats/targets exactly. Existing workspace CAS/version/sync services own persistence; an old remote discarding condition controls cannot acknowledge success. Shared variable values remain unchanged by running conditions or scenarios.

## Necessary implementation evidence

Actual API fixtures demonstrate extraction-dependent conditions, condition mutation isolation, false no-script/no-network/no-history, fixed repeats, a backwards loop exiting on changed variables, two data iterations and unchanged canonical workspace. Other actual cases cover invalid/nonboolean/throwing/infinite condition failures without private diagnostics, missing/disabled branch targets, repeat limits,1000-step back-edge termination and logout while a condition child is live preventing any request. A remote fixture refuses synchronization after dropping the condition. Formats proves screened disabled conditions/importable references and exact explicit backups.

Worker tests prove host-observed booleans and rejection of asynchronous/nonboolean results, plus existing native-work timeout, child cancellation/reaping, bounded-output/privacy and ordinary script-result regressions. Editor tests prove stable target identity across reorder, condition/repeat persistence and incoming-branch cleanup. Report UI distinguishes condition skips, script skips and declarative iteration endings; bilingual catalogs, TypeScript, production frontend and scoped Clippy are checked. These are targeted implementation checks, not the final unified review.

Parallel request batches are now available; see [parallel coverage](SCENARIO-PARALLEL-COVERAGE.md). Nested group editing, multi-step parallel branch graphs, standalone visual graph orchestration, scheduled/durable jobs, persisted reports, broader protocols and all other unfinished matrix capabilities remain required before the final main-branch release. No local Docker or package/release build was performed.

Owned durable report summaries/diagnostics and JSON/CSV/JUnit/bilingual HTML exports are now available; see [saved report scope and evidence](SAVED-RUN-REPORT-COVERAGE.md). Detailed response linking, richer report comparison/sharing and scheduling remain unfinished.
