# Published Markdown snapshot coverage

Scope: first hosted profile of `documentation-004`, `documentation-005`, `documentation-006` and `documentation-014` under [published-markdown-snapshots.md](specs/published-markdown-snapshots.md). Full documentation-site parity remains open.

An authenticated hosted owner can publish 1–32 explicitly selected saved Markdown documents whose `secret` flag is false. The server checks the saved revision, distinct IDs, 1 MiB total source limit, 20 active / 256 retained version limits and a client idempotency key. Each publication stores an immutable snapshot in the shared database outside workspace backup/sync. The public JSON route returns only the chosen site title, document titles, folder labels and Markdown sources. The owner can list active and revoked versions and revoke one; a revoked key cannot republish by retry. Workspace deletion removes versions transactionally. Offline desktop cannot publish.

The public page renders one document at a time with the existing safe Markdown renderer. Raw HTML is skipped, remote image syntax displays alt text without fetching, and `moleapi:` request links remain inert. Owner controls require a confirm dialog naming the chosen documents and warn that publication needs no login and does not auto-update. Public page/API responses use no-store, no-referrer, nosniff and restrictive CSP headers.

Local evidence at the current feature branch: `published_docs` tests covered owner/foreign/anonymous access, private selection rejection, immutable source after workspace edits, idempotent retry, revoked-key conflict, revocation and deletion. The configured database test includes publication across two app instances, concurrent creation at the 20-active limit, and rejection after 256 retained versions; local SQLite passed, while PostgreSQL/MySQL require their CI endpoints. All 415 frontend tests, TypeScript, production 46-chunk build, embedded server build, scoped strict server Clippy and focused server tests passed. A real hosted browser published a public document next to a private sentinel, opened the URL in a separate anonymous browser at 390 px, saw no sentinel, HTML execution, image fetch or horizontal overflow, then verified old content after editing and saving the source. Revocation changed the public page/API to 404, and a second version showed the updated source. Owner-panel axe reported zero violations and one incomplete theme/background contrast check; anonymous public-page axe reported zero violations and zero incomplete checks. Static page and public JSON headers were checked from the embedded server.

Independent read-only review found that the static frontend fallback returned HTTP 200 for revoked or malformed `/docs/{id}` despite the public API returning 404. A dedicated HTML route now checks the same database publication state before serving the page; the static fallback refuses unmatched `/docs` paths. Focused route tests and a rebuilt embedded server confirmed 404 for revoked, malformed and extra-segment URLs while an active version returns 200. The review also identified missing concurrent/limit evidence; the configured-database tests now cover both boundaries. No remaining confirmed Important finding was reported in that review.

Subsequent browser work found that a new root-level document used `collection_id: null` in the unsaved draft while the server omitted the optional field in its response. A save succeeded but the client kept marking the workspace dirty, blocking publication until reload. Root creation and moving a document back to the root now omit the optional value; a save-acknowledgment regression covers the server's omitted-field response. Focused editor tests and TypeScript pass, with full frontend/build and browser recheck required at the new head.
