# Persistent scheduled runs

Owned workspaces now provide named collection/scenario schedules with cron, IANA timezone, enabled state, selected canonical environment/dataset and iteration settings. Croner4.0.1 parses five/six-field expressions with optional seconds; chrono-tz0.10.4 supplies timezone rules. Preview returns five upcoming UTC instants. Fixed-time jobs in a DST gap follow Croner's documented roll-forward to the first valid instant; the bilingual UI explains this and supports preview before saving. An omitted environment follows the workspace's current active environment through the existing runner; the UI labels this explicitly. No custom cron parser or protocol executor is introduced.

## Storage and execution

Configuration and queued/running/last state use owned schedule documents. Editor CAS revision is independent of operational updates. An additional SeaORM migration indexes document kind/revision; schedule document revision stores the next wake timestamp, allowing bounded indexed scans instead of loading all definitions. Workspace deletion uses the existing ref-ID cascade. Job ledgers retain the latest100 records per definition and store only fixed outcome/error codes, counters, UTC timestamps and report IDs, without session tokens, bodies or variable values.

The router owns an engine lifetime guard; scan/job tasks do not keep that guard alive. Dropping the owning router cancels its execution tasks. A two-slot engine scans at bounded intervals and uses the existing runner's capacity, network policy, scripts, environments/datasets, privacy/history and reports. Hosted enabled definitions continue after logout, although logout still cancels already active owner work through existing fencing. Local desktop tasks require the application/runtime to stay running.

A transaction locks workspace then schedule, rechecks current state and assigns a job ID with a600-second lease before execution. Matching leases prevent another engine from claiming the same definition concurrently. Scheduled cursors advance from current time rather than replaying every missed occurrence. Queue-now permits one pending manual occurrence, including on disabled tasks. Active branches share the ordinary300-second run budget. Expired leases become interrupted/canceled ledger records; prior uncertain network effects are not retried under the same job ID. A later queued or scheduled occurrence can proceed. Completion is fenced by matching job ID and preserves later configuration edits. Severe clock skew/process failure does not provide exactly-once network effects; external distributed runner enrollment remains unfinished.

Cancellation signals are persisted and watched independently while the run future continues to be polled. This avoids freezing the runner while a watchdog waits for the single SQLite connection. Config updates cancel obsolete pending/active work without silently changing the new definition. Definition deletion cancels its work and removes its job ledgers. Failed start/capacity, report save failure and interruptions use fixed diagnostics rather than returning copied credentials.

## Interface and API

Authenticated owned list/create/update/delete, cron preview, queue-now, cancel and execution-history routes verify owner/workspace and canonical references. Each workspace holds at most100 definitions. The React/Radix management section selects collection/scenario/environment/saved dataset, cron/timezone/iterations and enable state, previews timestamps, edits by config revision, queues/cancels runs and opens saved reports through the existing report viewer. Chinese/English fixed labels and task statuses are translated; definitions keep user text unchanged. Tasks are operational state of the serving instance, not yet synchronized workspace definitions.

## Necessary implementation evidence

Six actual API fixtures cover genuine cron execution with selected scenario/environment/two-row dataset/private report, two engines sharing SQLite claiming one disabled manual run once, operational updates preserving editor revision/CAS conflicts, owner isolation/preview/queued cancellation/workspace cascade, queue persistence across router restart and expired-lease interruption without replay, in-flight cancellation, and hosted execution after logout. The shared-database case exposed a watchdog/runner single-connection deadlock; an independently polled watchdog fixes it, and the fixture now finishes with exactly one observed HTTP request. Mature library tests verify optional seconds, IANA rejection and the documented DST gap behavior.

Frontend cases cover preview and saved references without copied variables, report selection, existing runner UI and bilingual catalogs. TypeScript, production frontend and scoped Clippy passed. Only changed paths were repeated after failures or new changes. Real PostgreSQL/MySQL multi-process, native OS lifecycle and rendered/browser verification remain for the final unified phase.

Notification channels, distributed runner enrollment/configuration/scaling, broader monitoring/performance, task/artifact synchronization, richer scenario graph/parallel branching and all other remaining matrix features are still required before unified review, main merge/branch cleanup and the new GitHub Actions release. No local Docker or package/release build was performed.

Scheduled completion/interruption notification targets and durable delivery records are now available; see [notification scope and evidence](NOTIFICATION-COVERAGE.md). Extra integration/event bindings and distributed runner capabilities remain unfinished.
